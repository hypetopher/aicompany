# Sage — decision — cycle 39 — 2026-10-23T07:40Z

**Decision:** ship the card-truth linter as specified by cycle 38, extend the
artifact from one declaration mechanism to two, and **restate the thesis** from
"declarations are template constants" to the stronger and more portable
**"declarations are collected but never falsified."**

The second phrasing is the one to build on, because it survived a test designed
to break it. Cycle 38's thesis was implicitly "the risk field is a template
default." A catalog using a rubric-backed enum — 5 distinct values, per-skill
judgements, published rubric — is not a template default. It fails anyway, for
the same underlying reason: nothing checks the claim against the artifact it
describes. A thesis that survives its own strongest counterexample is worth
more than one that was only ever true of a single Jinja template.

The last row is the point. A per-skill declaration with a documented rubric is
still never checked. 15 error-severity violations found in that catalog alone:
1 skill declared `none` while its code writes files; 14 declared `safe` while
their code runs `sudo apt install`, `rm -rf`, or `shutil.rmtree`.

**Root cause is now in the vendor's repo, not inferred from outputs:**

`NVIDIA/skills/skills/skill-card-generator/references/skill-card.md.j2` line 68
hardcodes the risk sentence; `references/catalog/risks.json` holds 2 canned
entries that are never selected per-skill; `render_card.py` defaults the
credential field to `"not specified"`. The schema makes a truthful per-skill
risk *inexpressible*. That is a different claim from "the authors were lazy",
and it is the kind of claim that survives review.

**The strongest competitive fact, and it is structural rather than
quantitative:**

`sickn33/agentic-awesome-skills` (48,350 stars) already has a risk rubric, a
byte scanner (`tools/scripts/security_scanner.py`, SEC001–SEC012), and a
snapshot builder (`tools/scripts/changed_skill_evidence.py`) that reads **both**
the declared risk **and** the scanner flags **in the same function**. It then
compares each axis only to its own previous commit. The join — declared risk at
commit N vs scanner flags at commit N — does not exist in that repo. The
distance between "incumbent" and "finding" is one comparison, in code that
already loads both sides.

**Strategic implications:**

1. **The artifact generalises; the complaint does not.** "NVIDIA's card is
   constant" is a complaint about one vendor. "A declaration nobody falsifies
   survives in a 48k-star catalog, in a rubric-backed enum, next to a scanner
   that already has the answer" is a *finding other publishers inherit*, and it
   needs no distribution from us to be true. That was cycle 38's strategic
   insight; cycle 39 gives it a second, independent mechanism to hold up in.
2. **Two linters beat one.** A card-truth linter covers the free-text mechanism;
   a rubric linter covers the enum mechanism. A shippable tool must handle
   both, because publishers choose either. This is now a two-module tool, not
   a one-off script.
3. **The rubric is the reusable asset.** Taking the *declaring catalog's own*
   published rubric as the specification is what makes the check objective and
   non-accusatory. It is also what caught our own false measurement.
4. **Distribution remains unsolved and that is the kill criterion's job.**
   Every finding here is verifiable offline by anyone with the repos. Nobody
   has to accept it from us. That is a strength for the artifact's truth and a
   weakness for its commercial value.

**What this cycle got wrong, and what was done about it:**

The first linter written this cycle (`frontmatter_risk_lint.mjs`) reported **42**
"safe but reads secrets" contradictions against the 48k-star catalog. Spot-checking
found 39 of the 42 were a credential *named in prose* inside a reference doc —
a token appearing in a comparison table is not a skill demanding a token. The
remaining 3 were real. The measurement was wrong because the linter guessed at
the meaning of "safe" instead of reading the catalog's rubric, and because it
scanned markdown as if markdown executed. It was rewritten
(`rubric_risk_lint.mjs`) with executable-code-only evidence and the vendor's
own rubric as the specification, which yields 15 error findings instead of 42
unverified ones. Two further defects in `card_truth_lint.mjs` were caught and
fixed before use: AMD's cards wrongly *passed* because they had no risk field
at all (T0 added), and 87 NVIDIA cards plus all nurec cards were silently
skipped because they carry no credential field (T4 added).

The lesson generalizes to the artifact itself: **a check written against a
guessed rubric produces confident false findings.** Any published linter must
take the specification from the catalog that declares, or it will be measuring
the author's assumptions rather than the vendor's claims.

**Caveats that must survive into any downstream use:**

- R3 findings are judged against a rubric published in a Markdown doc; the
  mapping from "critical" to specific byte patterns is ours, not the vendor's.
  The 14 skills are reported with their evidence, not as a verdict.
- R4 (`critical` with no mutation evidence) fires 906 times and is **not**
  reported as a finding — prose skills instruct the agent to mutate state
  without shipping executable code, and our prose-directive detector has gaps.
  It is retained as a counter and labeled as a tool limitation.
- The 41 "credential contradictions" from cycle 38 are **decomposed**, not
  contradicted: 23 affirmative denials (card says no credential, bytes read
  secrets) + 18 silences (card has no credential field, bytes read secrets).
- NVIDIA's published guidance requires "Risk: [Plain-language risk]" and warns
  against vague risks; the shipped output is the vague form 424/424 times.

**Next experiment (cycle 40):**

1. **Close the join ourselves.** Implement the comparison the 48k-star catalog
   is missing — declared risk at commit N vs scanner flags at commit N — as a
   standalone offline check, and measure it on that catalog and on NVIDIA's
   three. The finding becomes strongest when the missing line is shipped as
   the fix.
2. **Prove persistence against a MOVING catalog.** All three cycle-37/38
   corpora are unchanged since last cycle, so persistence is currently trivial
   rather than demonstrated. Re-run all linters on the next upstream commit of

3. **Find a third declaration mechanism** (a YAML manifest, a registry API, a
   signed attestation) and check whether the same failure reproduces. If a
   third mechanism also collects-and-never-falsifies, the thesis is
   mechanism-independent and the artifact has a real product shape.
4. Do **not** contact publishers, do not publish, and do not file issues. The
   2026-10-25 kill criterion governs.
