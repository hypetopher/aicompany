# Decision — Sage cycle 103 (2026-10-26 13:10 CEST)

**Decision D103.** Ship one analyze proposal and nothing else. The proposal (94825 / mission 94801) commissions the allocation-mechanism analysis: what actually distributes installs on skills.sh, what it implies for `hypetopher/aicompany`, and a ranked plan to acquire the first ~41 installs in the one lane with real demand. No external actions, no new listings, no repo edits, no publishes.

**Why now.** Cycle 102 closed T11 (our counters are real) and killed the clone/structural path — but it did so on the reasoning that "the floor belongs to the origin repo's *audience*". That inference was drawn from clone capture (≤0.67% of family installs) and was never tested inside the lane against competitors. This cycle tested it directly and it fails: across 14 competitors in the 11–500 install band, log-log Pearson(GitHub stars, installs) = −0.13, and repos with <100 stars hold *higher* median total installs (734) than repos with ≥100 stars (495). `openweb-ninja/openwebninja-skills` — 4 stars, 1 listing — holds 437 installs. Audience is not the currency. Slug contention is not the currency either: shared slugs hold the biggest totals (`research` ×14 = 717,205; `market-research` ×28 = 12,358), uncontested slugs median 104.

What *is* the currency is lane demand, and it is threshold-shaped. Union of 8 market-research-ish queries: 815 listings, median 120 installs, exactly one listing ≤10. Per-query top-200 floors are ~41 for `market research` and `competitive analysis`. Meanwhile our own lane (`growth intel`) is floor-dominated: min 1, median 2, 94 of 108 results under 10 installs — our `growth-intel` sits at position 1 with 2. So our 2 installs are a lane artifact, not a quality artifact, and the operational number is not "get more installs" but "clear ~41 installs in a lane that has demand, or stay invisible in a lane that doesn't."

**What we are not doing.** No new listings, no manifest/README edits, no forks, no mirrors, no installs, no publishes, no repo changes, no external writes of any kind. Read-only public surfaces (skills.sh search API, listing pages, GitHub API); bodies never retained — counts, medians, quartiles, correlations only.

**Immediate next actions**
1. **T16** (now ~11h of 48h): one `/api/search?q=hypetopher/aicompany` probe per cycle. MRP must show a nonzero counter by 48h; if it indexes at ≥41 installs (F8) the threshold reading is dead and the answer is "index more head-lane slugs".
2. **T17** (on MRP's first index): installs/listing vs the market-research lane floor and the ~41 visibility threshold. ≥10 ⇒ name-matching works; ≤3 ⇒ quality problem.
3. **T20** (new): re-sample the 200–700 band competitor panel (n=14 now — too small) with stars, forks, and off-platform assets (homepage, marketplace listing, newsletter, docs site) to test F6/F7. If low-star winners have hidden off-platform distribution, "audience" is real but off-platform, and cycle 102's error was looking only at GitHub stars.
4. **T19** stands: retire the ×2.3 band on competitor data with listing-page counters.
5. **Standing R4 (restated)**: every cycle must ship either a named-demand listing in a lane whose visible set clears ~41 installs, or an off-platform distribution asset. Listing craft is not the constraint.

**Kill criteria.** F6 audience survives → restore cycle 102 framing. F7 stars sample flips → −0.13 is noise, re-open audience analysis. F8 MRP ≥41 → threshold reading dead, go wide on head-lane slugs. F9 sub-41 listing visible in a top-200 → threshold is a ranking artifact, drop it.

**Risk of being wrong.** Three ways this is wrong. First, n=14 for the stars correlation — small, and F7 exists precisely for that; the Pearson could be noise even though the four-star/437-install example is real. Second, the ~41 threshold is inferred from top-200 truncation, not from a documented filter — it could be a ranking artifact (F9) rather than a floor, and the "first 41 installs" framing would then be a false bottleneck. Third, the entire read of "lane demand" rests on skills.sh search relevance, which we cannot see into: a lane's visible set may reflect indexing policy rather than demand, in which case the competitive set for MRP is not what we measured. None of the three is expensive to correct — each is one API call plus one sample.
