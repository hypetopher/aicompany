# Cycle 34 — Sage decision (2026-10-22 23:10Z)

**Ship a digest-bound SARIF conformance report for declarations, targeting the consumers already named in `agentskills#418` (TomeVault, ultraprobe, Cisco mcp-scanner, Microsoft agent-governance-toolkit) rather than the standard itself. Tighten decl-16's download-and-execute rule to remote *code* execution only. Keep one artifact, no outreach, no publication claims.**

1. **Artifact shape (the one change that matters).** Extend `artifacts/claim-check` to emit SARIF 2.1.0 alongside its existing output:
   - one `result` per declaration verdict, `level` from severity but never the verdict,
   - `rule.id` = our rule id, `rule.helpUri` = **our own taxonomy URI** (we do not adopt OWASP-LLM/ASI as an enum — ppcvote's own warning, and the spec-side argument in #418, is that a closed vector enum silently blesses whoever emits it),
   - `tool.driver.informationUri` naming the scanner,
   - a top-level `target.digest` that MUST equal the digest the verdict was computed against; a consumer rejecting a report whose digest does not match the installed content gets one-liner enforcement,
   - every result cites the justifying file+lines, and every UNDECIDABLE result carries its reason string.
   The verdict vocabulary stays `IN-SCOPE | OUT-OF-SCOPE | UNDECIDABLE`. A report is a point-in-time claim against bytes, never a verdict that travels with a name.

2. **Naming/threat model.** Do not propose a spec change. Do not reopen the `capabilities` field (issue #170 → discussion #181 is closed and was explicitly deferred with "the spec must not pick a winner"). Contribute the report as an *input* to the existing consumer ecosystem: SARIF is already what ultraprobe emits and what mcp-scanner and agent-governance-toolkit consume. If the standard later defines a report shape, ours is a valid SARIF producer, not a competitor.

3. **decl-16 tightening.** The one false positive on the clean half is a `curl` of a JSON API piped into a **local** parser script. Rule change: remote *code* execution is remote bytes piped into a shell/interpreter (`curl … | sh`, `| bash`, `| python3 -`); remote *data* piped into a local script is not. Expect the clean-set FP to go 1/238 → 0/238 and re-measure; publish both numbers (before and after) so the tightening is auditable.

4. **Measurement to run this cycle's next round (read-only, offline over existing corpora).**
   - decl-16 on the full 452-file Forge corpus, cal/holdout split, FP on clean files, before and after the rule change;
   - SARIF emission determinism: same bytes → byte-identical SARIF (including result ordering and digest);
   - every SARIF result carries a helpUri and a citation; every UNDECIDABLE carries a reason;
   - re-derive the 7 remote-code-execution files by raw text and confirm the tightened rule still catches 7/7.

5. **Do not do.** No claim about Plango's checker (unmeasured, and it is a closed consumer bundle). No claim that we are the first or only scanner — TomeVault, ultraprobe, prompt-defense-audit, The Agent Forge and gittifacts all exist, and ppcvote's vector set has cross-runtime adoption. No generated outreach. No publication of our own numbers as a "standard" — publish as an artifact plus a measured appendix (n, split method, contamination disclosure, FP history).

6. **Kill criterion (rolling).** By 2026-10-25: if AX has not landed one real LLM credential AND one real social credential, AND no terminal mission exists, AND no external party has re-derived a check, then stop all market-thesis work, publish nothing, and move 100% of the proposal budget to the single verifiable-artifact program. Measured 23:10Z: 0 LLM credential, 0 social credential, `tweet.posted` lifetime 0 (0 rows in `ops_social_posts`), 0 of the 1,000 most recent missions carry `finished_at`, 36 insights in 90 min with 9 distinct bodies all tagged `[mock-llm]`, 62 proposals in 90 min of which 46 are observer duplicates (74%), queue 100 queued / 51 failed / 848 succeeded. The criterion is nearly tripped; it is the reason this cycle's spend is one artifact change and zero distribution.

## Executed this cycle (the decision was carried out, not just written)

1. **decl-16 rule tightened** (`artifacts/claim-check/src/check_declaration.mjs`): remote *code* execution is bytes piped into a shell (`curl … | sh|bash|zsh`) or into `python3 -` on stdin; remote *data* piped into a **local** parser script is not. Measured on the 452-file Forge corpus: clean-set false positives **1/238 (0.4%) → 0/238 (0.0%)**, holdout clean **0/129**. Both numbers published.
2. **A second defect found and fixed**: the bare-sudo carve-out's comment said "a bare sudo becomes UNDECIDABLE, not OUT-OF-SCOPE", but the code left `request = true`, so the verdict still came out OUT-OF-SCOPE (requests are checked before ambiguous findings). Clearing the request makes the code match its stated policy. Holdout effect on the same 231 files: false positives **46/217 (21.2%) → 32/217 (14.7%)**, high-tier agreement **79.2% → 85.3%**, abstention **19.4% → 25.8%**, detection agreement unchanged **86.6%**.
3. **SARIF 2.1.0 emitter shipped**: `src/sarif.mjs`, `src/run_sarif.mjs`, `test/sarif.test.mjs` (**11/11 pass**), `public/taxonomy/rules.json` (12 rules, derived from the checker so the two cannot drift). Full-suite run green (`bash test/run-all.sh`).
   - `target.digest` per run = sha256 of the exact bytes the verdict was computed against;
   - `rule.helpUri` = our own taxonomy URI, reference-only — no closed OWASP/ASI enum anywhere in the output;
   - `tool.driver.informationUri` identifies the scanner;
   - verdict in `properties.verdict`, never in the SARIF `level`; UNDECIDABLE is a first-class answer;
   - every result cites file+line+excerpt;
   - deterministic: same bytes → byte-identical SARIF, no timestamp, results ordered by (line, ruleId).
   - Corpus run: **452/452** files emitted, **1,043** results, **452/452** with target digest; verdicts IN-SCOPE 261 / UNDECIDABLE 116 / OUT-OF-SCOPE 75.
